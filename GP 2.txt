================================================================================
                                ABSTRACT
================================================================================

The widespread adoption of Internet of Things (IoT) devices, such as IP cameras, routers, and embedded sensors, has significantly expanded the network vulnerability surface. Standard signature-based security tools—including standard firewalls and Intrusion Detection Systems (IDS)—frequently fail when facing high-frequency scanning, zero-day vulnerabilities, or automated botnet attacks like Mirai [4]. To address this challenge, this graduation project presents an end-to-end network honeypot threat detection and visualization system. The platform is specifically configured to simulate Dahua IoT device log outputs, capturing and analyzing unauthorized access attempts in real time.

The system is organized into three major layers:
1. Ingestion and Persistence Layer: A lightweight FastAPI (Python) backend utilizing an asynchronous ingestion pipeline. This module receives honeypot log payloads in single-event or batch formats and normalizes them into structured schemas. It supports dual persistence, operating on local SQLite databases for edge configurations and remote PostgreSQL (via Supabase) for distributed, multi-sensor deployments.
2. AI Inference Engine: A security analysis module that aggregates raw log events by source IP. It utilizes an unsupervised Isolation Forest machine learning model [3] combined with heuristic rules. By analyzing traffic dimensions (such as authentication failure rates, unique password attempts, and suspicious system command strings), the engine automatically classifies the attack type (e.g., Brute Force or DDoS), calculates a numerical risk score, and assigns a corresponding threat level (Low, Medium, or High).
3. React Visualization Dashboard: A web interface built with Vite and vanilla CSS. The dashboard provides network administrators with real-time telemetry streams, geographical threat maps mapping IP origins, and interactive firewall controls for immediate incident mitigation.

Simulation testing using automated security traffic generators shows that the FastAPI backend processes batch log uploads with sub-millisecond local database latency. Furthermore, the unsupervised Isolation Forest model yields accurate threat classifications, isolating malicious scanner IPs from normal connection profiles. The proposed architecture offers a scalable and cost-effective approach to monitoring decentralized networks, transforming raw security telemetry into actionable administrative insights.

Keywords: Honeypot, FastAPI, React.js, Artificial Intelligence, Isolation Forest, 
          IoT Security, Anomaly Detection, Real-time Visualization.

1.1 Overview
Over the past decade, Internet of Things (IoT) devices—including IP cameras, network routers, and smart hardware—have become globally integrated into network infrastructures. However, these systems are often manufactured with minimal built-in security, leaving exposed administrative interfaces, unpatched vulnerabilities, and simple default credentials. Attackers deploy automated scanning networks and malware frameworks (such as the Mirai botnet) to systematically probe public IP subnets, compromising hundreds of low-power devices in short periods to coordinate Distributed Denial of Service (DDoS) networks [4], [8].

Standard defensive systems, including static firewalls and signature-based Intrusion Detection Systems (IDS), remain highly reactive [2]. They rely on pre-configured databases of known security threats, making them ineffective at blocking zero-day vulnerabilities, dynamic brute-force traffic, or stealthy scans that closely match authorized administrative access. While machine learning anomaly detection is a viable alternative, applying it in active network environments has historically been restricted by high false-positive rates and significant processing overhead [5]. To bypass these issues, network security operators use honeypots [1], [7]. These are decoy network resources designed with no corporate or commercial function. Because the honeypot has no legitimate users, any incoming traffic is immediately treated as suspicious or malicious, providing clean security data.

1.2 Problem Statement
Developing a highly responsive threat intelligence system for IoT networks requires solving several specific engineering issues:
1. Log Ingestion Overheads: IoT security sensors are usually physically separated from central databases. Standard log-forwarding applications are too resource-heavy for edge hardware, requiring a lightweight web API to capture events without dropping packets.
2. Ingestion Thread Blocking: Submitting raw honeypot events to heavy machine learning engines on a single thread blocks the HTTP loop. If the backend is forced to clean data and execute inference synchronously, it will experience severe response lag during high-frequency scans [5].
3. Signature-Bypassing Scans: Static, rule-based security filters are easily bypassed by security scanners that rotate usernames, slowly vary request rates, or utilize unique payload structures. The system needs a dynamic anomaly detection model that profiles behavioral patterns instead of matching hardcoded strings [3], [6].
4. Telemetry Interpretation: Sifting through thousands of raw JSON lines or syslog entries in a security crisis is impractical. Administrators require a real-time, lightweight graphical interface that translates raw network logs into a structured spatial and temporal map of active attacks.

1.3 Aims and Objectives
The principal aim of this project is to develop and validate a high-throughput honeypot threat detection system with an integrated machine learning classifier and a real-time visual monitoring dashboard. To achieve this, we set the following objectives:
1. To design a decoupled HTTP REST API using FastAPI that securely ingests single and batch honeypot log payloads using a shared key handshake.
2. To implement a dual-persistence database layer supporting local embedded environments (using SQLite) and scalable production databases (using remote Supabase/PostgreSQL) with full foreign key constraints.
3. To develop an asynchronous background worker pipeline utilizing secure OS file-locking to schedule and run ML evaluation without interrupting client ingestion loops.
4. To build an unsupervised Isolation Forest classifier [3] in Python, combining it with heuristic rules to extract behavioral features (e.g., failed logins, credential density, connect patterns) and classify threats into Brute Force and DDoS.
5. To develop a web-based React monitoring dashboard featuring an interactive SVG world coordinate map, live log feeds, and active port isolation controls using vanilla CSS.

2.2 Artificial Intelligence in Cyber Anomaly Detection
Most industrial networks still rely on signature-matching engines like Snort [2] to flag malicious traffic. While highly effective for known CVE exploits, signature matching cannot detect novel zero-day attacks or stealthy, slow-frequency scans. Modern security research focuses heavily on machine learning models for anomaly detection [5].

Unsupervised machine learning is valuable for threat detection because network security datasets are highly imbalanced, with normal traffic dwarfing attack logs [6].
1. K-Means Clustering: Attempts to group traffic based on feature distances. However, K-Means is highly sensitive to outliers and struggles with the non-spherical data shapes typical of network intrusion attempts.
2. Isolation Forest (IF): Developed by Liu et al. [3], the Isolation Forest isolates anomalies instead of profiling normal clusters. Because anomalies have distinct values and are sparse, they require far fewer random splits to isolate, making them appear closer to the root of decision trees. This design runs with minimal memory and processing overhead, making it highly suitable for real-time traffic analysis.

2.3 Real-Time Dashboard Systems
Standard security information systems (such as corporate SIEMs) are expensive, require significant computing footprints, and introduce latency when parsing raw log feeds. They rarely offer the lightweight, responsive geographical mapping needed to quickly locate and block an attacker during an active scanning wave.

Modern decoupled web architectures (built on FastAPI and React.js) provide a highly responsive alternative. Moving the data processing to a dedicated API layer allows administrators to view live threat coordinates and update firewall states from a standard web browser.

3.3 Asynchronous Pipeline and Scheduling
To ensure high responsiveness, batch log uploads are managed asynchronously.
1. The FastAPI backend receives the batch, structures it into chunks of 25 logs, and assigns a unique `pipeline_id`.
2. The server responds to the client immediately, offloading the processing to background threads.
3. An asynchronous worker writes the chunk to a shared file, acquiring an OS-level file-lock (`.dahua_logs.lock`) to prevent collisions.
4. The worker executes `ai.py` in a separate process, passes the logs, and releases the file-lock.
5. The machine learning results are stored and linked to the database, allowing the frontend to poll and render pipeline progress in real time.

3.4 AI Core: Isolation Forest & Heuristic Classification
The security evaluation module utilizes a two-layer approach:
- Heuristic Profiling (Rule-Based): Fast, static checks. If an event contains credentials or a password attempt (`login.failed` or `login.success`), it is categorized as a "Brute Force" attempt. If it represents a simple port connection (`session.connect`), it is tagged as "DDoS".
- Machine Learning (Isolation Forest): Dynamic behavioral analysis. For each unique source IP, the system extracts a set of network statistics over a sliding time window. The Isolation Forest model evaluates this feature vector to separate active, high-density attackers from normal scanning patterns [3].

3.5 AI System Mathematical Logic & Feature Engineering
The Isolation Forest model [3] isolates anomalies by recursively splitting feature spaces using binary decision trees. Let X = {x_1, x_2, ..., x_n} be a dataset containing n samples of d-dimensional network features. An Isolation Tree (iTree) is built by randomly choosing an index feature 'q' and a split point 'p' until either the tree reaches its maximum depth or the samples are fully isolated.

The path length h(x) is the count of edges traversed from the tree root to the leaf node where the sample falls. The anomaly score s(x, n) is calculated as:

  s(x, n) = 2^{ - \frac{E(h(x))}{c(n)} }

Where:
- E(h(x)) is the average path length of x across the collection of isolation trees.
- c(n) is the average path length of an unsuccessful search in a binary search tree (BST) built with n nodes, defined as:
  
  c(n) = 2 \ln(n - 1) + 0.5772156649 (Euler's Constant) - \frac{2(n - 1)}{n}

Scoring ranges:
- If s is close to 1.0, the path length is very short, indicating that the target IP was easily isolated and represents a highly anomalous, dangerous security event.
- If s is below 0.5, the sample falls deep within normal clustered traffic profiles.

Feature Vector Construction:
For each unique source IP, the system engineers a 6-dimensional feature vector:
  f(IP) = [C_success, C_failed, C_commands, C_suspicious, C_connections, U_passwords]
Where:
- C_success: Counts successful log attempts.
- C_failed: Counts failed log attempts.
- C_commands: Counts system commands input.
- C_suspicious: Counts dangerous commands (e.g., wget, curl, chmod, rm).
- C_connections: Counts overall handshake connections.
- U_passwords: Counts unique password variations tried by the IP.

3.7 AI Scoring and Aggregation Pseudocode
The following pseudocode details the algorithmic implementation of our machine learning feature extraction and Isolation Forest scoring logic:

================================================================================
ALGORITHM: AI_Anomaly_Detection_And_Scoring
================================================================================
INPUT: Raw Dahua log records L
OUTPUT: Aggregated attack records with threat severity classification

BEGIN
  1. Initialize rows = []
  2. FOR EACH line IN L DO:
       IF line is valid JSON format THEN
         Parse line and append to rows
       END IF
     END FOR
  3. Load rows into a pandas DataFrame (DF)
  4. Ensure standard columns exist: src_ip, eventid, protocol, username, password, input, timestamp
  5. Fill all empty cell values with empty string ""
  6. Parse "timestamp" column to DateTime format
  
  7. Extract Feature groups:
       login_success = Filter DF where eventid contains "login.success"
       login_failed  = Filter DF where eventid contains "login.failed"
       commands      = Filter DF where eventid contains "command.input"
       connections   = Filter DF where eventid contains "session.connect"
  
  8. Define suspicious patterns S = ["wget", "curl", "chmod", "rm", "nc", "bash", "sh"]
  9. FOR EACH command IN commands DO:
       IF command.input contains any pattern in S THEN
         Mark is_suspicious = True
       ELSE
         Mark is_suspicious = False
       END IF
     END FOR
  
  10. Generate Feature Vector for each UNIQUE src_ip:
        success_count = Count(login_success group by src_ip)
        failed_count = Count(login_failed group by src_ip)
        command_count = Count(commands group by src_ip)
        suspicious_commands = Sum(is_suspicious group by src_ip)
        connection_count = Count(connections group by src_ip)
        unique_passwords = UniqueCount(password group by src_ip)
        
  11. Merge counts into a master Features DataFrame
  12. IF count of unique IPs >= 3 THEN
        Initialize IsolationForest(contamination=0.4, random_state=42)
        Fit IsolationForest on [success_count, failed_count, command_count, 
                                suspicious_commands, connection_count, unique_passwords]
        Predict anomaly label (-1 for anomaly, 1 for normal)
      ELSE
        Set anomaly label = 1 for all
      END IF
  
  13. FOR EACH IP in Features DO:
        IF connection_count >= 10 AND failed_count == 0 AND command_count == 0 THEN
          Set attack_type = "DDoS"
        ELSE IF failed_count >= 1 OR unique_passwords >= 2 THEN
          Set attack_type = "Brute Force"
        ELSE
          Set attack_type = "Brute Force"
        END IF
        
        # Calculate Severity Heuristics
        IF attack_type == "DDoS" THEN
          IF connection_count >= 20 THEN severity = "High"
          ELSE IF connection_count >= 10 THEN severity = "Medium"
          ELSE severity = "Low"
        ELSE IF attack_type == "Brute Force" THEN
          score = (failed_count * 2) + (success_count * 3) + (unique_passwords * 2)
          IF score >= 8 THEN severity = "High"
          ELSE IF score >= 4 THEN severity = "Medium"
          ELSE severity = "Low"
        END IF
      END FOR
      
  14. Export master Features DataFrame to attack_results.json
END

4.3 Core API Route Contracts
- Ingestion routes:
  1. `POST /honeypot/events`: Accept raw JSON from honeypots. Returns a 201 status on success. Requires `X-Shared-Secret` header.
  2. `POST /honeypot/events/batch?chunk_size=25`: Accepts a list of honeypot events. Returns a JSON structure containing `pipeline_id`, `events_received`, and `chunks_queued`.
- Reporting routes:
  1. `GET /report/alerts?limit=20`: Returns a list of enriched alerts, merging the original attack_event, raw/normalized logs, and AI predictions.
  2. `GET /report/pipelines/{pipeline_id}`: Returns the current pipeline stats (e.g., status: running/completed, total_events, chunks_sent, predicted_events).
  3. `GET /report/summary`: Exposes aggregated statistics used to paint frontend charts, such as total attack volume, average threat level distributions, and active attacker IP locations.

4.4 Asynchronous Task Management & File-Lock Logging
A major challenge was preventing file-access collisions when multiple background threads wrote log data to `dahua_logs_multi.json` simultaneously. To resolve this, we implemented a lightweight, OS-independent file locking helper in `ai_client.py`. The lock utilizes atomic operating system flags (`os.O_CREAT | os.O_EXCL`) to create a temporary `.dahua_logs.lock` file. If the lock is held by another process, the current process sleeps and retries after a 100ms back-off delay.

5.2 Technical Challenges & Limitations
Despite the successful implementation, several technical constraints were identified:
1. In-Memory Pipeline Overhead: The pipeline status tracking is currently managed in the backend's RAM. Restarting the FastAPI server clears active pipeline logs and historical progress metrics (though persistent event data remains intact).
2. Database Latency: Remote cloud persistence (Supabase) introduces network overhead, which can become a bottleneck during sustained, multi-gigabyte log floods.
3. Static Feature Bounds: The Isolation Forest requires a minimum of 3 unique IPs in its training set to build distinct isolation trees [3]. If less than 3 IPs are present, the model defaults to heuristic categorization.

5.3 Future Directions & Scalability
To transition this prototype into a highly resilient, enterprise-scale network security ecosystem, we propose the following future avenues of development:
1. Distributed Message Brokers: Replacing the REST batch ingestion with a dedicated, fault-tolerant message broker, such as Apache Kafka or RabbitMQ, will allow the system to ingest millions of events per second across multi-node honeynets.
2. Sequence-based Deep Learning: Migrating the AI model from tabular features (Isolation Forest) to deep sequence models, such as Recurrent Neural Networks (RNNs) or Transformer models, to analyze the precise temporal sequence of shell commands and detect advanced persistent threats (APTs).
3. Active Automated Firewalls: Integrating the backend API with real-world network orchestrators, allowing the dashboard's "Gate Controller" to issue active firewall rules (e.g., via iptables or cloud security group APIs) to automatically block malicious IPs in production.
4. Distributed Honeynets: Deploying decentralized high-interaction honeypot nodes globally, forwarding telemetry to a centralized cloud-hosted FastAPI backend for collaborative global threat mapping.
